# Architecture and mechanics

## Project layout (maintained repo, v4 baseline)
- `main.lua`: standalone bundled output generated by `build.py`; this is what loadstring consumers fetch.
- `00_hub.lua`: hub UI + main parry automation.
- `03_minigames_fix.lua`: mining timing and harvesting-ring automation using received client round information and simulated normal player input; keep working behavior.
- `06_parry_learning.lua`: pure timing estimator with bounded consensus and persistent JSON schema v1.
- `test_parry_learning.luau`: portable estimator test (requires Luau CLI).
- `verify_hub.lua`: in-game GUI, toggle, unload and re-run smoke verification; not a parry-accuracy test.
- `publish.py`: publishing helper; check generated bundle and protect concurrent remote changes.

## Runtime state and integration
- Global handles: `getgenv().CRLF_HubController` and `getgenv().CRLF_Minigames`; lifecycle should stop/unload previous version and disconnect listeners.
- Relevant accessible client library: `ReplicatedStorage.Modules.Packets`; combat packet `Packets.Combat.packets.BlockInput.send({Action="Block Input"})`, release `{Action="End Block"}`.
- **Observed client-source behavior:** game `CombatClient` repeats Block Input while key F is held and releases using End Block. Do not dismiss packet repetition as inherently incorrect. It still requires sanity checks, release deadlines and bounded throughput.
- Replicated character state attributes used: `State_Parrying`, `State_ParriedAttack`, `State_ParryCooldown`, `State_Blocking`, `State_SwordBlocking`, `State_Attacking`, `State_Stunned`, `State_BlockBroken`. `StateManager.CanParry` also guards cases such as blocking, dodging, incapacitation, flying, skill use, occupied and attack states; static replicated checks are not necessarily identical to the real game's function.
- Current broad detector listens to nearby humanoids' `AnimationPlayed`, checks nonlooping/length exclusion, actor alive, weapon/tool, facing and distance; tracks imminent threats per animation.
- Initial v4 constants from repo: RANGE 24 studs, POINT_BLANK 10, GRANT_LATENCY 0.10s, PARRY_WINDOW 0.25s, PARRY_COOLDOWN 1.05s, SESSION 0.16s, unknown WINDUP_DEFAULT 0.40s. **These are code defaults / developer comments, not universally verified constants**.
- Seed windup table in v4: `125957249913572` = 0.92s; `73629219095110` = 0.90s; both must be treated as tentative correlations.
- Old v4 BENIGN animation table included `73807165586659`; v4.1 removed exclusion because earlier telemetry's interpretation was inconclusive. **Removal does not prove it is an attack.**
- Learner stores `CloverRPG/parry_learning_<PlaceId>.json`, schema `{version:1,records:{"animation_id":{time,count}}}`; its last seven samples undergo median agreement before updates.
- Avoid reinitializing `recentAttacks` in `watch()`, avoid duplicate tracks, and disconnect listeners on death/respawn/unload.

## Execution caveats
- Madium supports a varying set of executor-specific APIs; gate file APIs, `gethui()`, packet availability and synthetic key support with capability checks where possible.
- `AnimationTrack.TimePosition` and playback speed offer better time alignment than assuming wall-clock time since replicated `AnimationPlayed`.
- Existing animation tracks must be adopted on discovery; `AnimationPlayed` only sees future starts.
- Multiple threats must be individually scheduled; don't lose later attacks when finishing an earlier one.
- A defensive hold and a **successful parry** are different outcomes. Attribute-based confirmation is more trustworthy than just observing BlockInput or a lack of damage.
